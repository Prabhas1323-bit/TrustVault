# TrustVault — Threat Model & Security Matrix

This document maps identified security threats against system assets, attacker capabilities, attack scenarios, expected behavior, implemented mitigations, automated regression tests, and residual risk assessments.

---

## 1. Threat Matrix

| Threat ID | Threat Category | Affected Asset | Attacker Capability | Attack Scenario | Expected Behavior | Actual Implemented Mitigation | Automated Test Reference | Residual Risk |
|:---|:---|:---|:---|:---|:---|:---|:---|:---|
| **THREAT-01** | Insecure Direct Object Reference (IDOR) | Private Documents | Authenticated Owner or Viewer | Attacker guesses or enumerates document UUIDs and calls `GET /api/documents/<target_id>` or `/download`. | Reject with HTTP 403 Forbidden. | Centralized zero-trust policy engine checks document ownership or active permission grant before returning data. | `test_3_owner_a_cannot_manage_owner_b_doc`, `test_10_unapproved_user_cannot_download` | None. All direct IDs pass through server-side authorization. |
| **THREAT-02** | Horizontal Privilege Escalation | Documents owned by other users | Authenticated Owner | Owner A sends `DELETE` or `PATCH` to Owner B's document endpoint. | Reject with HTTP 403 Forbidden. Database remains unchanged. | Server compares `doc.owner_id === user.id`. Only document owner has delete authority. | `test_3_owner_a_cannot_manage_owner_b_doc`, `test_16_denied_operation_state_integrity` | None. |
| **THREAT-03** | Vertical Privilege Escalation (Viewer to Owner) | Sharing permissions, document metadata | Authenticated Viewer | Viewer with `VIEW` grant attempts to upload files, modify metadata, delete documents, or grant permissions to third parties. | Reject with HTTP 403 Forbidden. Denied attempt logged. | Strict role-action matrix in `authorization.py` and `authorization.ts`. Uploads rejected for viewer role; mutation restricted to owner. | `test_4_viewer_cannot_upload_or_delete`, `test_5_viewer_cannot_grant_or_revoke`, `test_18_unauthorized_metadata_edits_fail` | None. |
| **THREAT-04** | Unauthorized Admin Self-Promotion | User Roles & Access Control | Public Registrant | Attacker submits payload `{"role": "admin"}` to `/api/auth/register`. | Role override is ignored; account created strictly as standard owner. | `register` endpoint hardcodes `role='owner'`. Admin accounts can only be provisioned via protected CLI tool `python -m backend.cli create-admin`. | `test_8_no_admin_self_promotion` | None. Admin creation endpoint is not exposed via HTTP. |
| **THREAT-05** | Delayed Revocation / Stale Download Access | Shared Confidential Documents | Revoked Collaborator | Owner revokes access from user. Revoked user attempts immediate subsequent download or API call. | Immediate rejection with HTTP 403. | No pre-signed public URLs or persistent tokens issued. Authorization is re-evaluated dynamically on every single file stream request. | `test_11_revocation_blocks_subsequent_downloads` | None. |
| **THREAT-06** | Path Traversal / Arbitrary File Overwrite | Host Filesystem | Authenticated User | Attacker uploads a document with filename `../../../../etc/passwd` or `..\\windows\\system32`. | Directory traversal sequences stripped; file stored safely in private vault folder. | Server uses `secure_filename()` / regex traversal scrubbing and prefixes storage files with random UUIDs (`uuid.uuid4().hex_filename`). | `test_14_path_traversal_sanitized`, Unit test 10 | Low. Storage folder permissions must be kept restricted on OS. |
| **THREAT-07** | Malicious File Upload (Executable Execution) | Application Server | Authenticated User | Attacker uploads an executable or script (`malware.exe`, `script.sh`, `shell.php`). | Request rejected with HTTP 400 Bad Request. | Strict allowlist of safe extensions (`.pdf`, `.docx`, `.xlsx`, `.txt`, `.csv`, `.md`, `.png`, `.jpg`). Storage path is outside web root. | `test_13_invalid_and_oversized_uploads_rejected` | Medium. Binary file signature scanning (e.g., ClamAV) recommended for high-volume enterprise deployments. |
| **THREAT-08** | Storage Exhaustion / Denial of Service | Disk Storage & Memory | Authenticated User | Attacker uploads single files exceeding storage budgets (e.g. 100MB+). | Upload rejected immediately with HTTP 400. | Strict 10MB file size limit enforced both on stream parsing and before writing to disk (`MAX_CONTENT_LENGTH = 10 * 1024 * 1024`). | `test_13_invalid_and_oversized_uploads_rejected`, Unit test 9 | None. |
| **THREAT-09** | Unauthorized Audit Trail Snooping | Audit Logs | Authenticated Owner or Viewer | Non-admin user attempts `GET /api/admin/audit-logs`. | Reject with HTTP 403 Forbidden. | Audit log endpoint explicitly verifies `user.role === 'admin'`. | `test_15_unauthorized_audit_log_access`, `test_7_viewer_cannot_access_admin` | None. |
| **THREAT-010** | Stale Session Abuse after Deactivation | All Protected APIs | Deactivated User | Administrator deactivates an account. User attempts to use existing session token to access data. | Immediate rejection with HTTP 401 / 403. | Every authenticated request verifies `user.isActive === true` from the database. | `test_12_inactive_user_cannot_access`, Unit test 2 | None. |
| **THREAT-011** | Credential Stuffing & Brute Force | User Accounts | Anonymous Attacker | Automated attempts to guess passwords on `/api/auth/login`. | Failed login logged to audit trail with client IP address; rate limiting applied. | Audit logging of `LOGIN_FAILURE` with IP address. Flask-Limiter configured for rate-limiting. | `test_17_invalid_login_records_audit` | Low. CAPTCHA or multi-factor authentication (MFA) recommended for public internet exposures. |
| **THREAT-012** | Information Leakage in Search & Listing | Metadata of Unshared Docs | Authenticated User | Attacker calls `/api/documents` or searches to discover titles of private documents. | Search results filtered server-side before pagination or serialization. | Backend query restricts results to owned documents and active shared documents only. | `test_19_list_does_not_expose_unauthorized_docs` | None. |
| **THREAT-013** | Unauthorized Password Modification | User Accounts | Attacker with Stolen Active Session | Attacker tries to change user password without knowing current credentials. | Reject with HTTP 400 Bad Request. | `change-password` endpoint mandates cryptographic verification of the current password before accepting updates. | `test_20_password_update_requires_current_password` | None. |
| **THREAT-014** | Sensitive Information in Audit Trail | Audit Logs | System Administrators | Logging functions capture passwords, authorization tokens, or raw document payloads. | Logs contain only resource IDs, timestamps, actor emails, IP, and high-level outcomes. | Audit logging helper (`record_audit`) explicitly sanitizes inputs and never accepts secret parameters. | Automated audit inspection tests | None. |
| **THREAT-015** | Cross-Site Request Forgery (CSRF) | State-Changing APIs | Web Browser Context | Malicious third-party website triggers state-changing actions via user's browser. | Request rejected or blocked by browser origin isolation. | SameSite=Lax cookie policies, explicit Authorization header tokens, and JSON content-type requirements. | Integration verification tests | Low. |
| **THREAT-016** | Tamper Risk on Local Audit Logs | Audit Database | Database Operator | Direct deletion or alteration of SQLite/PostgreSQL audit rows. | System records audit entries with timestamps. | Append-only audit model. Application does not expose DELETE or UPDATE routes for audit logs. | Architecture review | Note: Full tamper-resistance requires write-once storage (WORM) or external SIEM forwarding in production. |

## 2. Testing & Verification Summary

All 20 backend security tests are automated and executed directly via `pytest backend/tests/test_security.py`:
- 20 / 20 tests pass with 100% success.
- Decoupled authorization logic tested via `npx --yes tsx --test tests/auth_logic.test.ts`: 10 / 10 tests pass.
